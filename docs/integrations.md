## Emby (4.10.2.0)

Référence : `openapi_v3.json` du tag `4.10.2.0` (ci-dessus), noté **[spec]** ; pages lisibles sur https://dev.emby.media/reference/RestAPI.html.

- **Clé d'API** [V] : en-tête `X-Emby-Token` ou paramètre `?api_key=` (schéma `apikeyauth` de la [spec]). L'appli envoie l'en-tête.
- **Ids** [V] : `Id` des éléments, utilisateurs et serveur sont des chaînes ([spec] `BaseItemDto.Id`, `UserDto.Id`) ; l'appli accepte aussi un nombre par prudence.

### Webhooks Emby

- Ils nécessitent Emby Premiere [V] (https://emby.media/support/articles/Webhooks.html : « With Emby Premiere you can setup webhooks »).
- La liste des évènements n'est pas publiée par Emby : seuls `library.new` et `library.deleted` sont cités par des messages du forum, et le payload ne contient aucun utilisateur. [?] non vérifiable sans Premiere et sans référence officielle ; l'appli ne s'en sert pas.
- Solution retenue : webhooks Radarr/Sonarr (évènement `Download`), puis vérification de la présence dans Emby avec `/Items`.

## Serveur multimédia : Emby, Jellyfin ou Plex (7.3)

Un seul serveur actif, choisi dans l'assistant (réglage `mediaServer`, champ `kind`) ; l'ancien réglage `emby` en tient lieu tant que `mediaServer` n'a jamais été enregistré. Tout passe par l'interface `MediaServer` (`src/server/integrations/media-server.ts`), une implémentation par type : `emby.ts` (inchangée), `jellyfin.ts`, `plex.ts`. Aucun de ces serveurs n'a été essayé sur une instance réelle pour ce lot : les points [?] ci-dessous sont à vérifier le jour où l'un d'eux remplace Emby.

### Plex

Sources : Seerr (`src/utils/plex.ts` pour le code PIN, `server/api/plextv.ts`, `server/api/plexapi.ts`, `server/lib/scanners/plex/index.ts`, `server/entity/Media.ts`), forum Plex (https://forums.plex.tv/t/authenticating-with-plex/609370). Plex ne publie pas de référence complète de ces API.

- **Configuration** : adresse du serveur et **jeton du propriétaire** (`X-Plex-Token`), testés en direct : `GET /` du serveur (`MediaContainer.friendlyName`, `version`, `machineIdentifier`), puis `GET https://plex.tv/api/resources?includeHttps=1` (XML) : le serveur doit y figurer (`Device clientIdentifier = machineIdentifier`) avec `owned="1"`, sinon le jeton est refusé. [?] `machineIdentifier` dans la réponse de `/` : probable d'après Seerr, à confirmer.
- **En-têtes** : `X-Plex-Product: Request` et `X-Plex-Client-Identifier` stable (empreinte HMAC de la clé de chiffrement de l'installation : rien de plus à enregistrer, et la clé n'en sort pas). `Accept: application/json` pour le serveur et les codes PIN ; `/api/users` et `/api/resources` de plex.tv répondent en XML, lu par un petit lecteur maison (`xmlElements`).
- **Connexion d'un membre (code PIN)** [V d'après Seerr] : le serveur de l'appli crée le code (`POST https://plex.tv/api/v2/pins?strong=true`) pose un cookie signé (`httpOnly`, `SameSite=Strict`) qui désigne ce code pour ce seul navigateur, et ne lui donne que l'adresse `https://app.plex.tv/auth/#!?clientID=…&code=…&context[device][product]=Request`, ouverte dans une fenêtre. Le navigateur interroge l'appli toutes les 2 s (`POST /api/auth/plex/pin/check`, avec ce cookie) ; l'appli interroge `GET https://plex.tv/api/v2/pins/{id}?code=…` jusqu'à `authToken`. Code expiré (`expiresAt`, 15 minutes par défaut s'il manque) ou inconnu de plex.tv (404) : 410. [?] `expiresAt` au format ISO : à confirmer.
- **Jeton du membre** : il sert une seule fois, dans la même requête : `GET https://plex.tv/users/account.json` (compte), puis il est oublié ; jamais écrit en base ni en journal.
- **Droit d'entrer** [V d'après Seerr] : le compte du jeton est celui du propriétaire (même id que le compte du jeton enregistré) → administrateur, donc premier propriétaire de l'appli ; sinon il doit être dans `GET https://plex.tv/api/users` (XML, jeton du propriétaire) avec un `<Server machineIdentifier>` égal à celui du serveur. Sinon : 403 « Ce compte Plex n'a pas accès à ce serveur ». [?] cas des membres de « Plex Home » (gérés) : non vérifié.
- **Import des membres** : le propriétaire et les amis ayant accès à ce serveur (même liste `/api/users`) ; ids = ids de comptes plex.tv. Photos : adresses `https://plex.tv/…` ou `https://*.plex.tv/…` seulement, relayées sans jeton.
- **Bibliothèques** : `GET /library/sections` ; une section sans agent (`com.plexapp.agents.none`) n'a pas d'ids et n'est pas proposée ; `movie` → films, `show` → séries.
- **Disponibilité** : balayage de `GET /library/sections/{id}/all?includeGuids=1`, pages de 200 (`X-Plex-Container-Start`/`X-Plex-Container-Size`), ids lus dans `Guid[].id` (`tmdb://603`, `tvdb://121361`, nouvel agent) ou dans `guid` (`com.plexapp.agents.themoviedb://…`, anciens agents). Même cache de 5 minutes que Jellyfin. Un titre connu seulement par son id IMDb n'est pas reconnu (Seerr le résout par TMDB : pas fait ici).
- **Épisodes** : `GET /library/metadata/{ratingKey}/children` (saisons), `leafCount` = épisodes présents. [?] `leafCount` compte-t-il les épisodes sans fichier ? Plex ne liste normalement que les fichiers présents.
- **Ajoutés récemment** : `GET /library/sections/{id}/all?includeGuids=1&sort=addedAt:desc`. Sans le jeton du membre (jamais gardé), la rangée est la même pour tous (DECISIONS.md). [?] une série ressort à la date de son premier ajout, pas à celle de son dernier épisode.
- **Lien « Regarder dans Plex »** [V d'après Seerr] : `https://app.plex.tv/desktop#!/server/{machineIdentifier}/details?key=%2Flibrary%2Fmetadata%2F{ratingKey}`, sans adresse publique à régler.
- **Webhooks Plex** : réservés au Plex Pass ; non utilisés (les webhooks Radarr/Sonarr et le balayage suffisent).

## Sonarr 4.0.20 (API v3)

Auth et base identiques à Radarr. Code : https://github.com/Sonarr/Sonarr/tree/v4.0.20.3014 (chemins relatifs à `src/`). Doc : https://wiki.servarr.com/sonarr/settings#connections

- **TMDB vers TVDB** : `GET https://api.themoviedb.org/3/tv/{id}/external_ids` donne `tvdb_id`, parfois null. Prévoir ce cas.
- **Lookup** [V] : `GET /series/lookup?term=tvdb:121361` (`SeriesLookupController`). Contient `seasons[]` avec `seasonNumber` et `monitored`.
- **Ajout** [V] : `POST /series`.
  - Champs : `title`, `tvdbId`, `qualityProfileId`, `rootFolderPath`, `monitored`, `seasonFolder`, `seriesType` (`standard`, `anime`, `daily`), `seasons[].monitored`.
  - `addOptions` (`NzbDrone.Core/Tv/AddSeriesOptions.cs`) : `searchForMissingEpisodes`, `searchForCutoffUnmetEpisodes`, et hérite de `MonitoringOptions` : `ignoreEpisodesWithFiles`, `ignoreEpisodesWithoutFiles`, `monitor` (`unknown`, `all`, `future`, `missing`, `existing`, `firstSeason`, `lastSeason`, `pilot`, `recent`, `monitorSpecials`, `unmonitorSpecials`, `none`, `skip`).
  - L'appli n'envoie pas `monitor` : il vaut alors `unknown`, qui suit `LegacySetEpisodeMonitoredStatus` (`EpisodeMonitoredService.cs`) : tous les épisodes d'une saison `monitored: false` sont désactivés. Les saisons demandées seules sont donc suivies [V].
  - `languageProfileId` : propriété en lecture seule qui vaut toujours 1 (`SeriesResource.cs`) [V]. Ne pas l'envoyer en v4 ; l'appli ne lit `/languageprofile` que pour une version < 4.
- **Disponibilité** [V] : `seasons[].statistics` (`SeasonStatisticsResource`) : `episodeFileCount`, `episodeCount`, `totalEpisodeCount`, `sizeOnDisk`, lus sur `GET /series/{id}`.
- **Liste** [V] : `GET /series` donne toutes les séries avec `tvdbId`, `tmdbId` (présent en v4, `SeriesResource.cs`) et `seasons[].statistics`. Sans `tmdbId` (v3), l'appli passe par `tmdb.tvdbIdFor` puis garde l'id TVDB dans `media.tvdb_id`.
- **Queue** [V] : `GET /queue?page=n&pageSize=200&includeEpisode=true`, mêmes champs que Radarr avec `seriesId`, `episodeId` et `seasonNumber` au premier niveau (`Sonarr.Api.V3/Queue/QueueResource.cs`) ; `includeEpisode` ajoute l'objet `episode`, dont l'appli ne lit que `seasonNumber` en repli. Un enregistrement par épisode.

- Adresses : `POST /api/webhooks/radarr` et `POST /api/webhooks/sonarr` (méthode **POST**, valeur par défaut de Radarr/Sonarr ; PUT refusé). Jeton en `?token=` dans l'adresse, ou en-tête `X-Webhook-Token` via le champ `Headers` (réglage avancé, présent dans Radarr 7.0.3 et Sonarr 4.0.20 [V]) ; adresses et jeton dans `GET /api/settings/webhooks` (propriétaire).

## Seerr 3.5.2 : import des demandes (6.2)

Auth : `X-Api-Key: <clé>` (Paramètres › Général), base `/api/v1`. Code au tag `v3.5.2` : https://github.com/seerr-team/seerr/tree/v3.5.2 (`server/routes/request.ts`, `server/entity/User.ts`, `server/entity/MediaRequest.ts`, `server/constants/media.ts`, `server/constants/user.ts`, `seerr-api.yml`). L'adresse et la clé servent à l'appel seulement, jamais enregistrées (`POST /api/import/seerr`, propriétaire).

- **Demandes** [V] : `GET /request?take=100&skip=n&filter=all`. Réponse `{ pageInfo: { pages, pageSize, results, page }, results: [], serviceErrors }`, où `pageInfo.results` est le total. `take` vaut 10 par défaut et n'a **aucun plafond** (ni dans la route, ni dans `seerr-api.yml`) ; `skip` avance quand même du nombre de demandes reçues. Tri par défaut : `request.id` décroissant.
- **Filtre** [V] : `filter=all` (ou absent) couvre les cinq statuts de demande, mais seulement les médias aux statuts 1 à 5 et 7 : une demande dont le média est **bloqué (6)** n'est jamais renvoyée. Pour une demande 4K, c'est `media.status4k` qui est filtré.
- **Demande** [V] (`MediaRequest`) : `id`, `status`, `type` (`movie`/`tv`), `is4k`, `createdAt`, `updatedAt`, `serverId`, `profileId`, `rootFolder`, `tags`, `isAutoRequest`, `media` (`mediaType`, `tmdbId`, `tvdbId`, `status`, `status4k`…), `seasons[]` (`seasonNumber`, `status`), `requestedBy`, `modifiedBy`, `seasonCount`, `profileName`, `canRemove` (gestionnaire).
- **Dates** [V] : des `Date` sérialisées par `JSON.stringify`, donc ISO 8601 en UTC (`2026-10-01T18:30:12.000Z`), que la base soit SQLite (`datetime`) ou Postgres (`timestamp with time zone`, `server/utils/DbColumnHelper.ts`).
- **Statuts** [V] (`server/constants/media.ts`) : demande 1 en attente, 2 approuvée, 3 refusée, 4 échec, 5 terminée ; média 1 inconnu, 2 en attente, 3 en cours, 4 partiel, 5 disponible, 6 bloqué, 7 supprimé. (Overseerr, branche develop, a aussi les statuts de demande 4 et 5.)
- **Membre** [V] : `requestedBy` est l'entité `User` entière (seul `settings` est retiré par `toJSON`) : `id`, `email`, `username`, `plexUsername`, `jellyfinUsername`, `jellyfinUserId`, `userType`, `displayName` (= `username` › `plexUsername` › `jellyfinUsername` › `email`), etc. Il n'existe pas de champ `embyUserId` : un compte Emby a `userType` 4 (`server/constants/user.ts`) et son id Emby dans `jellyfinUserId`, recopié tel quel depuis `User.Id` de la réponse d'Emby (`server/routes/auth.ts`), donc au même format que l'id du membre dans l'appli.

Correspondances (`services/seerr-import.ts`) :

- **Membre** : `jellyfinUserId` comparé à l'id Emby du membre, sans casse ni tirets (simple précaution) ; sinon `jellyfinUsername`, `username`, `plexUsername`, `displayName` comparés au nom du membre, sans casse (un nom porté par deux membres ne compte pas). Aucun membre créé : les demandes d'un compte sans correspondance sont écartées et listées.
- **Statut** : 1 → `pending` ; 2 → `sent` (déjà envoyée par Seerr, jamais renvoyée), ou `available` si le média (`status4k` pour une 4K) vaut 5 ; 3 → `declined` ; 4 → `failed` (relançable) ; 5 → `available`. Autre statut, titre sans `tmdbId`, série sans saison : écartée (« titre non reconnu »).
- **4K** : gardée (`is_4k = 1`), la colonne existant déjà ; `markAvailable` ne la fait jamais passer disponible avec la version ordinaire.

## Discord (5.3)

Facultatif, désactivé par défaut. Source : https://discord.com/developers/docs/resources/webhook#execute-webhook

- **Réglage** : Réglages › Notifications Discord (propriétaire), hors assistant. Adresse du webhook, interrupteur, évènements envoyés (`requested`, `approved`, `declined`, `available`, `failed`). `GET/PUT /api/settings/discord` et `POST /api/settings/discord/test`. L'adresse est un secret : chiffrée en base, renvoyée seulement sous la forme `{ set: true }`, gardée si le champ est laissé vide à l'enregistrement.
- **Adresse acceptée** : `https://discord.com/api/webhooks/{id}/{jeton}` ou `discordapp.com`, rien d'autre (aucun appel sortant vers un hôte choisi par l'utilisateur).
- **Appel** : `POST {adresse}` avec `{ embeds: [{ title, description, color, timestamp, fields, thumbnail }], allowed_mentions: { parse: [] } }`. Réponse 204 sans corps (sans `?wait=true`) [V]. `allowed_mentions` vide : un titre ou un motif ne peut pas mentionner `@everyone`. Limites : 1024 caractères par champ, 4096 pour la description (textes tronqués). Limite de débit (429) : pas de nouvelle tentative, le message est perdu.
- **Contenu** (en français) : titre court de l'évènement (« Demande approuvée »), `**Titre** (année)`, champ « Demandé par », champ « Motif » (refus) ou « Raison » (échec). Un message par évènement, pas par destinataire : l'acteur n'est pas exclu, un salon n'est pas un destinataire. Mêmes évènements que la cloche : une nouvelle demande d'un rôle à approbation automatique n'envoie pas « à approuver », ni les saisons ajoutées à une demande déjà en attente.
- **Affiche** : l'adresse TMDB publique (`https://image.tmdb.org/t/p/w342/…`) en vignette ; `/api/images` exige une session, Discord ne peut pas la lire. Sans affiche connue, pas de vignette.
- **Envoi** : après la validation de la transaction de l'évènement, sans attendre (l'action du membre n'en dépend jamais), délai de 5 s, aucune nouvelle tentative. L'évènement n'est envoyé que s'il est bien en base (une transaction annulée n'envoie rien). Désactivé ou sans adresse : aucun appel, ni vers Discord ni vers TMDB.
- **Journal** : l'échec est journalisé sans l'adresse (le jeton est dans le chemin, que `redactUrl` ne masque pas) : seulement la nature de l'erreur et son code HTTP.
- **Tester** : poste un message « Test de Request » avec l'adresse saisie, sinon l'enregistrée. Un refus de Discord (401/403, 404 si le webhook a été supprimé) devient une 422 au message lisible.
